# i2c-link-adapter

Хостовая утилита, которая соединяет **UNIX-сокет** с **CDC-портом**
платы `fntester_pcb`:

```
[клиент] --UNIX-сокет--> [адаптер] --CDC--> [плата] --I2C--> [мастер]
 модель                  утилита           slave         внешний
```

Утилита нужна, когда плата работает в **slave-режиме**: внешний
I2C-мастер обращается к плате, плата туннелирует транзакции хосту по CDC
(`SLAVE_EVENT`/`SLAVE_DONE`) и удерживает SCL, пока хост не ответит
байтами. Адаптер принимает эти события и отдаёт их вашему клиенту,
а ответ клиента отправляет обратно в плату.

## Зачем

- **Реальная плата вместо эмулятора.** В `--raw` сокет байт-в-байт
  совпадает с эмулятором (`/tmp/i2c_link.sock`), поэтому клиент,
  написанный под эмулятор, работает и с железом.
- **Модель устройства без протокола.** В `--semantic` клиенту не нужно
  знать про COBS/R и CRC-16: он получает текстовые события и отвечает
  байтами.
- **Отладочный контур.** Плата на столе, клиент на хосте, вся переписка
  видна в логах одного процесса.
- **Защита шины.** Если клиент не ответил вовремя, адаптер сам отвечает
  пустым пакетом, и плата отпускает SCL (мастер получает `0xFF`).

## Как работает

1. Утилита открывает CDC-порт (`/dev/ttyACM*`) в raw-режиме.
2. Настраивает плату под `--addr` и `--mode` (если не указан
   `--no-config`): `GET_CONFIG` → при необходимости `SET_SLAVE_ADDR`
   и `SET_MODE` → контрольный `GET_CONFIG`. Ответы на эти команды
   поглощает сам адаптер, клиенту они не мешают.
3. После завершения настройки создаёт UNIX-сокет и ждёт **одного**
   клиента. Второй клиент получает `ERR BUSY` и отключается. Если
   настройка не удалась (например, прошивка без slave-режима), сокет
   всё равно открывается: работать вручную в `--raw` можно.
4. Дальше работает выбранный режим:

### Режим `--raw` (по умолчанию)

Байты пересылаются как есть в обе стороны. Клиент сам говорит на
протоколе из `docs/data/protocol.md` (COBS/R + CRC-16). Настройка при
старте выполняется, пока клиент не подключён; если клиент уже есть,
адаптер в прозрачном режиме ничего не настраивает, чтобы не подмешивать
свои кадры в поток.

### Режим `--semantic`

Адаптер разбирает кадры от платы и печатает клиенту строки, а команды
клиента превращает в кадры протокола.

События от платы (адаптер → клиент):

| Строка | Значение |
|--------|----------|
| `EVENT <id> W <addr> <hex>` | мастер записал байты |
| `EVENT <id> WR <addr> <hex>` | записал, затем читает; **нужен ответ** |
| `EVENT <id> R <addr>` | мастер только читает — **нужен ответ** |
| `DONE W=<n> R=<n> <status>` | транзакция завершена |
| `WARN OVERFLOW` | данные обрезаны до 128 байт |
| `TIMEOUT` | клиент не ответил, отправлен пустой ответ |

`<id>` — номер события (0..127), `<addr>` — адрес slave в hex,
`<hex>` — байты в hex без разделителей (может отсутствовать),
`<status>` — код результата протокола в hex (`00` — успех).

Команды клиента (клиент → адаптер):

| Строка | Значение |
|--------|----------|
| `REPLY <id> <hex>` | ответ на событие `<id>`; пустой hex — `0xFF` |
| `REPLY <id>` | то же самое |
| `STOP` | закрыть ожидающее событие пустым ответом |
| `# ...` | комментарий |

Ответы адаптера: `OK` — принято, `ERR CMD` — неизвестная команда,
`ERR ARG` — нет или неверен `<id>`, `ERR ID` — ответ не на то событие,
`ERR BADHEX` — некорректный hex, `ERR NOPENDING` — нет ожидающего
события, `ERR TOOLONG` — слишком длинная строка.

Пример обмена (мастер пишет `10 20`, repeated start, читает `AA BB`):

```
EVENT 5 WR 42 1020     <- от адаптера
REPLY 5 AABB           <- от клиента
OK
DONE W=2 R=2 00
```

### Срок ответа

Пока устройство ждёт ответ, SCL удерживается, а мастер считает свой
таймаут: ~1 с у типичных Linux-адаптеров и 25–35 мс у строгих SMBus.
Поэтому у адаптера есть свой срок (`--reply-timeout`, по умолчанию
20 мс): если клиент не успел, уходит пустой ответ, плата отдаёт `0xFF`
и отпускает шину, а клиент получает `TIMEOUT`. Значение `0` отключает
автоматический ответ — тогда шину освобождает только `REPLY`/`STOP` или
отключение клиента.

### Обрывы

- Порт пропал (unplug, перепрошивка, reset) — адаптер закрывает его,
  ждёт и переоткрывает раз в 500 мс; после переоткрытия настройка
  повторяется.
- Клиент отключился при ожидающем событии — сразу отправляется пустой
  ответ.
- Сокет живёт всё время работы утилиты после первого успешного
  открытия порта.

## Сборка

```sh
cmake -S . -B build/host -DCMAKE_BUILD_TYPE=Debug
cmake --build build/host --target i2c-link-adapter
```

Бинарник: `build/host/utils/i2c-link-adapter/i2c-link-adapter`.
Для подробных логов собирайте с `-DCMAKE_BUILD_TYPE=Debug` (уровень
`dbg`). В release-сборке остаются `err`/`wrn`/`inf`.

## Запуск

```
i2c-link-adapter [options]

  --tty <path>          CDC-порт платы (default: /dev/ttyACM0)
  --listen <path>       UNIX-сокет (default: /tmp/i2c_link.sock)
  --semantic            семантический режим (события текстом)
  --raw                 прозрачный режим (по умолчанию)
  --addr <0x08..0x77>   адрес slave (default: 0x42)
  --mode <slave|master> режим шины (default: slave)
  --reply-timeout <ms>  срок ответа клиента (default: 20, 0 - без)
  --no-config           не настраивать режим при старте
  -h, --help            подсказка
```

Модель устройства в семантическом режиме:

```sh
i2c-link-adapter --tty /dev/ttyACM0 --semantic --addr 0x42
# в другом терминале:
socat - UNIX-CONNECT:/tmp/i2c_link.sock
```

Совместимость с эмулятором (тот же путь сокета, прозрачный режим):

```sh
i2c-link-adapter --raw --mode master
```

Для SMBus-мастера имеет смысл увеличить срок ответа:

```sh
i2c-link-adapter --semantic --reply-timeout 30
```

Пример клиента на Python (модель, которая отвечает записанными
байтами):

```python
import socket

sock = socket.socket(socket.AF_UNIX, socket.SOCK_STREAM)
sock.connect("/tmp/i2c_link.sock")
stream = sock.makefile("rw", newline="\n")

last = b"\x00"  # что отдавать в фазе чтения

for line in stream:
    parts = line.split()
    if len(parts) < 4 or parts[0] != "EVENT":
        continue

    event_id, kind = parts[1], parts[2]
    if kind in ("W", "WR") and len(parts) > 4:
        last = bytes.fromhex(parts[4])
    if kind in ("R", "WR"):
        stream.write(f"REPLY {event_id} {last.hex().upper()}\n")
        stream.flush()
```

## Ограничения

- Одновременно мастер и slave на одном блоке I2C быть не может;
  `--mode master` нужен для прозрачной работы с master-командами.
- Длина фазы чтения заранее неизвестна: верните столько байт, сколько
  мастер может прочитать, лишние не передаются.
- Сокет открывается только после того, как порт найден и настройка
  завершена. Если плата не подключена, утилита ждёт её и пишет об этом
  в лог.
- Утилита не является драйвером I2C: с `/dev/i2c-*` она не работает.

## Типичные проблемы

| Симптом | Причина и что делать |
|---------|----------------------|
| `device rejected slave mode` | прошивка без slave или адрес вне `0x08..0x77` |
| `device does not answer` | не тот порт, устройство занято; проверьте `--tty` |
| `ERR NOPENDING` | `REPLY` пришёл, когда события уже нет |
| `ERR ID` | ответ не на то событие; берите `<id>` из `EVENT` |
| `ERR BUSY` | уже подключён другой клиент, поддерживается один |
| `open /dev/ttyACM0 failed` | нет прав (`dialout`) или устройства ещё нет |
| Мастер получает `0xFF` | клиент не успел: увеличьте `--reply-timeout` |
